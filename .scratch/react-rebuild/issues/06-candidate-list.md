# 06: Candidate list and detail

**What to build:** The candidate list with Nearby / All scope, an explicit sort control and search, kept in sync with the map. Selecting a candidate opens the full evidence detail panel, and focus returns correctly when it closes.

**Blocked by:** 03 (Data to map)

**Status:** ready-for-agent

- [x] One visible-list selector (atlas, scope, sort, search) is the only source for both the list and the map markers. Nearby means the Nearby pool, read from the pool field. All means both pools.
- [x] Sort options: Scout order (Nearby only), Scouting index (descending), Component (water, shelter, darkness or security; descending). The default is Scout order for Nearby and Scouting index for All. Ties break by pool rank, then by ID.
- [x] Each card shows a pool and pool-rank label (for example "Nearby #2"), separate from its list position. It also shows its minimum round trip labelled as a straight-line lower bound with the route unverified. Wilderness context cards say they are beyond the six-mile minimum and for context only.
- [x] Search matches ID or name.
- [x] Selecting from the list highlights the marker and pans to it. Selecting a marker highlights the card.
- [x] The detail panel shows the scouting index as "N / 100", the four component bars, raw metrics, rationale, cautions, field checks, route status and location, plus the note that a weighted sum lets one component make up for another. Exact vector values and raster-estimated values are labelled as such.
- [x] Closing the detail panel returns focus to the card or marker that opened it.
- [x] UI copy follows the glossary. "Perfect spots" and "Recon list" are retired.
- [x] Vitest tests the selector with fixed expected orders for each scope and sort, tie-breaking and search.
- [x] Playwright: the Nearby default order matches the scout order, the All default order matches the index order, a keyboard user can reach a card and open and close its detail with focus returning, and list and map selection stay in sync.

## Comments

**Built and verified locally.** The full CI sequence passes: data check, type check, 56 Vitest tests (23 new), build, and 26 Playwright tests (11 new). The new browser tests also passed three times over with `--repeat-each=3`.

- **The selector** (`src/candidates/visibleList.ts`). `visibleCandidates(candidates, { scope, sort, search })` returns each visible candidate with its `position` and `poolRank` as separate fields. `sort` is the owner's pick or `null` for the scope's default, and `resolveSort` turns it into the sort in effect. Scout order chosen in Nearby falls back to the index in All, which is the rule ticket 07 needs for links. A component sort carries over when the scope changes. Leaving the default in place keeps each scope's own default, so Nearby → All → Nearby comes back to scout order. Nearby reads only the `pool` field, and a test relabels JP-02's pool to prove the selector doesn't fall back to a distance test.
- **Fixed orders.** The tests pin, by hand from `candidates.geojson`, scout order, the index order in both scopes, and every component order in both scopes. The real data exercises each tie-break: JP-02/JP-03 and EP-02/JP-07 tie on the index (pool rank breaks them), twelve candidates tie at water 90 (rank, then ID), and JP-02/EP-05/JP-10 tie on security. A synthetic pair covers equal keys and equal ranks in either input order.
- **One list for the cards and the markers.** `AtlasView` computes the visible list once and passes it to the list and to `MapView`. So **the map opens with the six Nearby markers, not 16**: Nearby is the default scope, as in the reference. Search filters the markers too. The 03 and 04 browser tests now switch to All where they need every marker. The legend lists only the pools that have markers on the map.
- **Selection.** Selecting a card highlights its marker and calls a new adapter command, `reveal`, which zooms to 14–15 and pans so the marker sits 140 px left of centre, clear of the panel, as the reference's `focusPoint` did (no offset below the tablet breakpoint; no animation with reduced motion). Clicking a marker highlights and scrolls its card into view but doesn't pan, so the map doesn't move under the pointer. A selected candidate that drops out of the visible list (scope or search) closes its detail panel.
- **Focus.** The selection records whether it was opened from the list or the map. The panel takes focus when it opens. Its × button or Escape closes it, and focus goes back to the card (by its DOM id) or to the marker (through a second new adapter command, `focusCandidate`). `MapView` exposes `reveal` and `focusCandidate` as a ref handle, because they're one-off commands, not state.
- **Sidebar tabs.** "Map layers" and "Candidates N" are ARIA tabs with arrow-key movement and a roving tab stop, as in the reference's tabs. Map layers is still the default tab. The count is the visible list's length, and a visually hidden live status announces it.
- **Cards** show the list position (an `<ol>`, so the number pill is `aria-hidden`), the name, "N / 100", the ID, a "Nearby #4" pool-rank chip, "2.2 mi minimum round trip", and either "Straight-line lower bound · route unverified" or "Minimum round trip over 6 mi · context only". The 6 comes from `manifest.constraints`. The reference's hard-coded "First access check" badge on EP-04 isn't ported: scout order already puts EP-04 first.
- **Detail panel** (`CandidateDetail.tsx`, which replaces the 03 card). It shows "N / 100" with "A relative index … It isn't a probability", the pool rank, four component bars as `role="meter"` with their weights from `method.json`, and the weighted-sum note. Then come eight raw metrics, each tagged *exact vector* (water and access distances), *60 m raster estimate* (canopy, slope, elevation, steep terrain; the 60 comes from `method.grid_resolution_m`), *straight-line lower bound* (round trip) or *mapped boundary* (GMU), with a line explaining why the figures can differ. After those: rationale, cautions, field checks, planning-limit chips from `manifest.constraints`, route status, and the location in WGS84. The provenance follows `docs/DATA_CONTRACTS.md`.
- **Schema.** Added as required: `rationale`, `cautions`, `route_status`, `gmu`, `metrics.elevation_ft` and `metrics.nearby_steep_terrain_percent` (all listed in the data contract). Added as optional: `field_checks` (a retained field) and `constraints.gain_ft` / `constraints.vehicle`. The real bundle passes unchanged.
- **Test fixture.** The real-bundle `DataSource` moved from `data.test.ts` into `src/atlas/testing/bundle.ts`, so the selector tests load the same validated atlas.
- **Colours.** A few small greys in the list and detail are a step darker than the reference's (for example `#8a967b` → `#6f7c61` for body text), heading towards AA contrast. Ticket 12 still owns the contrast audit.
- **Watch (12):** at the wilderness-wide fit, the Nearby markers overlap. The selected EP-06 (drawn 12% larger) covers EP-01, so a pointer can't click EP-01 until you zoom in. The list now gives full access. A "fit to East Portal" control like the reference's would help. The sidebar is still hidden below 800 px, so the list isn't reachable on a phone until 12's drawer lands.
- **Not in this ticket:** the field-status filter and the card status tags (08), the copy-coordinates button from the reference (the coordinates are plain selectable text for now), and the URL hash (07).
- **Bundle** is 513 kB of JS (154 kB gzipped).
